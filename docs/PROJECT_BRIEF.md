# GA360 电商漏斗与用户生命周期分析 · 项目完整说明

> 本文档描述项目当前的完整状态。所有数字均可在 `outputs/tables/` 中复核。

## 项目定位

这是一个基于 Google Analytics 360 Sample 的电商经营分析项目，分析对象是 Google Merchandise Store（Google 官方匿名化电商样本数据）。

项目的核心目标**不是**机器学习预测，**不是** A/B Test，而是用真实电商访问与购买数据，建立一套从数据审计、经营指标、转化漏斗、订单去重、用户价值分层到用户生命周期的完整分析链路。

外部想知道的三个业务问题：

1. 流量从哪里来，不同渠道的访问质量和购买效率有什么差异？
2. 用户从浏览商品到完成购买，主要在哪些环节流失？
3. 已经购买过的用户中，哪些更有价值、哪些适合维护、哪些适合召回？

项目真正的价值不是某一张学视图，而是走通了「原始数据 → 数据口径 → 指标计算 → 行为路径 → 用户价值 → 生命周期 → 业务建议」这条链路。

整个过程中最强调的一件事：**不能直接拿事件行数、Session 数、用户数、订单数混着算。** 电商数据天然存在多粒度问题——一个用户有多次访问，一次访问有多个行为事件，一个订单也可能在事件表中出现多行。口径不先拆清楚，后面所有转化率、订单数、收入和分层都可能是错的。

| `actionType` | 业务含义 | 事件行数 |

| 3 | 加入购物车 | 121,427 |

## 二、统计口径：项目最关键的基础

### 2.1 五级粒度

| 对象 | 标识 | 一行代表 |
|---|---|---|
| 用户 | `fullVisitorId` | 一个用户（去重即 UV） |
| 会话 | `session_key` | 一次访问 |
| 行为事件 | `actionType` + `hitNumber` | 一次行为，**不可当人数** |
| 订单 | 非空 `transactionId` 去重 | 一笔订单 |
| RFM | `fullVisitorId` | 一个购买用户 |

### 2.2 session_key 的修正过程（项目最关键的技术细节）

最初构造候选键：

```text
session_id = fullVisitorId + "_" + visitId
```

但没有直接采信，而是先做唯一性审计：

1. **DuckDB 六维审计**：按候选键分组，统计 `record_count`、`different_users`、`different_dates`、`different_channels`、`different_transactions`、`different_revenue`，用 `HAVING COUNT(*) > 1` 筛出重复。
2. **结果**：共有 **898 个**候选键重复，且形态高度一致——`record_count=2`、`different_users=1`、`different_dates=2`、`different_channels=1`、`different_transactions=0`、`different_revenue=0`。
3. **抽样核查**：抽取冲突样本逐字段比对，确认不是重复导入，而是同一用户同一 `visitId` 在两个不同日期各发生了一次真实访问。
4. **修正**：

```text
session_key = fullVisitorId + "_" + date + "_" + visitId
```

5. **验证**：Session 表 903,653 行 = 903,653 个唯一 `session_key`，重复为 0。漏斗事件表中 `session_key` 有重复属正常（一次会话可含多个行为）。

这个决定非常关键。**这个项目最难的不是 groupby 或画图，而是先确认每一行代表什么、用来连接和去重的 key 是否真的可靠。**

### 2.3 三个购买率，不可混用

| 指标 | 计算 | 值 |
|---|---|---:|
| Session 购买率 | 11,552 / 903,653 | **1.2784%** |
| 严格漏斗最终转化率 | 9,072 / 124,188 | **7.305%** |
| 用户购买率 | 10,022 / 714,167 | 1.403%（一般不对外用） |

Session 购买率的分母是全部会话（含跳出、无商品行为）；严格漏斗的分母只含"进入过商品详情页"的会话。**两者不能互相替代。**

### 2.4 两个收入，不可混用

| 口径 | 金额 | 用途 |
|---|---:|---|
| Session 表收入 | $1,540,071.24 | 经营与渠道分析 |
| 订单表收入 | $1,627,429.54 | 客单价与 RFM |

差 $87,358.30（约 5.7%），源于粒度差异与字段缺失。原则是：比效率用 Session 表，算客单价和 RFM 用订单表，**绝不在同一结论里混用**。

## 三、第一章：数据资产审计

审计的目的不是"读数据"，而是确认后续分析值得相信。

1. **确认路径与文件存在**：用 `pathlib` 定位项目根目录与两张原始表，避免读错版本——有时候读错文件不会报错，只是结论不对。
2. **按字符串读取标识符**：`fullVisitorId`、`transactionId` 指定 `string` 类型。它们是标识符不是数值，长 ID 按数字读取会丢精度（后续 Tableau 里也踩过同一个坑）。
3. **形状、字段、缺失检查**：确认会话表一行一次访问、事件表一行一个行为，两张表职责不同不能混用。
4. **候选键重复审计**（见 2.2）：DuckDB 六维聚合，发现 898 个重复键。
5. **冲突样本核查**：汇总统计只能说"有重复"，抽样才能说明重复的业务含义。
6. **重建 `session_key`**：两表同步创建，会话表唯一、事件表允许重复。
7. **actionType 编码审计**：确认只有 `[2,3,5,6]`，并统计各类事件行数（见 1.3）。

产物：`action_type_summary.csv`、`session_duplicate_audit.csv`、`session_conflict_sample.csv`。

## 四、第二章：经营基线与渠道分析

### 4.1 字段标准化

- `date`（YYYYMMDD）→ `analysis_date`
- `visitStartTime`（Unix 秒）→ `session_start`
- `transactionRevenue` ÷ 1,000,000 → `revenue_usd`
- `transactions` 缺失 → 0（`transaction_count`）
- `newVisits = 1` → 新用户，其余 → 回访用户
- `transactions > 0` → `has_transaction`
- `bounces = 1` → `is_bounce`

### 4.2 全站经营基线

| 指标 | 值 |
|---|---:|
| UV | 714,167 |
| Session 数 | 903,653 |
| 购买 Session 数 | 11,552 |
| Session 购买率 | 1.2784% |
| 交易数 | 12,115 |
| Session 表收入 | $1,540,071.24 |
| 跳出率 | 49.87% |

### 4.3 渠道表现（8 个渠道）

| 渠道 | Session | 购买率 | 收入 | 跳出率 | 流量占比 → 收入占比 |
|---|---:|---:|---:|---:|---|
| Referral | 104,838 | **5.076%** | **$651,429.91** | 25.98% | 11.6% → **42.3%** |
| Direct | 143,026 | 1.441% | $434,840.55 | 49.56% | 15.8% → 28.2% |
| Organic Search | 381,561 | 0.902% | $326,380.51 | 48.32% | 42.2% → 21.2% |
| Display | 6,262 | 2.284% | $78,337.46 | 35.87% | 0.7% → 5.1% |
| Paid Search | 25,326 | 1.852% | $43,558.90 | 38.01% | 2.8% → 2.8% |
| Social | 226,117 | 0.046% | $4,916.54 | **65.24%** | 25.0% → **0.3%** |
| Affiliates | 16,403 | 0.055% | $597.38 | 53.05% | 1.8% → ~0% |
| (Other) | 120 | 0.833% | $9.99 | 46.67% | — |

**核心结论：渠道的规模与效率严重错位。** 流量前三的 Organic / Social / Direct 没有带来对应收入，反倒是小流量的 Referral / Display 效率最高。

### 4.4 新老用户

| 用户类型 | Session | 购买率 | 收入 | 占比 |
|---|---:|---:|---:|---|
| 回访用户 | 200,593 | **3.528%** | $1,157,745.28 | 22.2% 流量 → **75.2% 收入** |
| 新用户 | 703,060 | 0.637% | $382,325.96 | 77.8% 流量 → 24.8% 收入 |

业务含义：新用户负责规模，回访用户负责效率。增长重心应从"拉新"转向"让新客变成回访"。

### 4.5 时间趋势

- 366 天日粒度指标；Session 数与收入的 Pearson 相关系数 **r = 0.3488**（弱相关）。
- 收入 Top5 日：2017-04-05（$27,150.61，仅 2,619 Session）、2017-02-14（$23,028.37）、2016-09-16、2016-08-25、2017-07-18。
- 流量 Top5 日全部集中在 2016-11（最高 4,807 Session，当天收入仅 $8,120.53）。
- **收入峰值与流量峰值不重合**，收入尖峰来自活动/客单价脉冲，而非流量驱动。

### 4.6 source/medium 下钻

按 `channelGrouping × source × medium` 拆出 288 个组合。**关键风险**：Referral 收入中 **94.47%** 来自单一 `(direct)/(none)` 组合（$615,391.69 / $651,429.91），而该标签实为"直接/自引"流量。

因此"Referral 高效"这个结论的**归因可靠性存疑**，它更像"高意图的直接/品牌流量"，而不是纯外部推荐。这也说明渠道解释不能停在 `channelGrouping` 一层。

## 五、第三章：严格转化漏斗

### 5.1 宽口径矩阵

按 `session_key × actionType` 透视成布尔宽表（`funnel_stage_matrix.csv`，132,577 行），只回答"这个 Session 是否出现过该行为"。**不判顺序**——出现过购买和浏览，不代表按正常路径完成。

### 5.2 严格顺序漏斗

按 `session_key` + `hitNumber` 排序，把事件序列压成列表，用状态机依次匹配 `expected = [2,3,5,6]`：

- `2→3→5→6`：完整通过
- `2→3→6→5`：出现了购买和结账，但顺序错，不算完成购买路径

产物 `strict_funnel_session_flags.csv`（132,577 行）。

### 5.3 整体漏斗

| 阶段 | Session | 占起点 | 相邻转化率 | 相邻流失率 |
|---|---:|---:|---:|---:|
| 浏览 | 124,188 | 100% | — | — |
| 加购 | 44,044 | 35.5% | 35.47% | **64.53%** |
| 结账 | 17,088 | 13.8% | 38.80% | **61.20%** |
| 购买 | 9,072 | 7.3% | 53.09% | 46.91% |

**核心洞察：最大流失不在支付，在"浏览 → 加购"（64.53%）。** 相反「结账 → 购买」通过率 53.09% 是全程最高——用户不是卡在付款，而是卡在"看一眼"到"想买"之间。

另算得：全站收入 ÷ 44,044 个加购 Session ≈ **每个加购 Session 对应 $34.97**。这把流失率翻译成了钱，用于给改版排优先级。

### 5.4 分组漏斗

**新老用户**（回访在每一步都领先，劣势是系统性的）：

| 用户类型 | 浏览 | 加购 | 结账 | 购买 | 最终转化 |
|---|---:|---:|---:|---:|---:|
| 回访用户 | 41,932 | 18,686（44.56%） | 9,123（48.82%） | 5,548（60.81%） | **13.23%** |
| 新用户 | 82,256 | 25,358（30.83%） | 7,965（31.41%） | 3,524（44.24%） | **4.28%** |

**设备**：

| 设备 | 浏览 | 购买 | 最终转化 |
|---|---:|---:|---:|
| desktop | 94,699 | 8,301 | **8.77%** |
| tablet | 3,646 | 122 | 3.35% |
| mobile | 25,843 | 649 | **2.51%** |

移动端约为桌面端的 1/3.5，折损最重在「加购→结账」（26.52%）和「结账→购买」（34.16%）。

**渠道**：Referral 27,192→4,315（15.87%，浏览→加购 45.45%、结账→购买 65.06%）；Display 1,461→118（8.08%）；Paid 5,073→374（7.37%）；Direct 21,110→1,423（6.74%）；Organic 62,659→2,788（4.45%）；Social 4,813→45（0.94%）；Affiliates 1,862→9（0.48%，加购→结账仅 15.02%）。

### 5.5 三维组合分析

`funnel_multi_dim.csv` 为「渠道 × 用户类型 × 设备 × 阶段」长表，共 184 行（46 个有数据的组合 × 4 阶段）。

- **最强组合**：`Referral × 回访 × desktop` 最终转化 **20.42%**（加购率 51.68%、结账→购买 67.97%）
- **最大未激活池**：`Organic Search × 新用户 × desktop`，浏览 31,354（占全部浏览 25.2%），转化仅 **3.54%**
- **负向叠加**：`Social × 新用户 × mobile` 最终 0.16%
- **伪优质**：`Affiliates × 新用户 × desktop` 加购率 37.6% 看似正常，但结账→购买仅 3.57%

**规范**：浏览量 < 1,000 的组合判为小样本噪音，不作为结论使用。

### 5.6 增量测算

以"同渠道回访用户转化率"为基准，与实际新客转化率的差值 × 浏览 Session 数：

| 组合 | 实际 | 同渠道回访基准 | 估算可撬动 |
|---|---:|---:|---:|
| Organic × 新 × desktop | 3.54% | 9.61% | **≈ +1,905 单** |
| Referral × 新 × desktop | 10.93% | 20.42% | ≈ +1,115 单 |
| Direct × 新 × desktop | 5.11% | 13.76% | ≈ +845 单 |
| Paid × 新 × desktop | 7.21% | 12.82% | ≈ +105 单 |
| Social × 新 × desktop | 0.70% | 3.44% | ≈ +70 单 |

**性质：这是乐观上限，不是预测。** 它假设新老差距完全由运营造成，而实际上老用户本身是自选择的高意向人群。

## 六、第四章：订单去重与 RFM 分层

### 6.1 订单审计

| 指标 | 数值 |
|---|---:|
| 购买事件行数 | 24,532 |
| 非空 `transactionId` 数 | 24,532 |
| 去重订单数 | **11,552** |

购买事件行数是订单数的 **2.12 倍**。直接拿事件数当订单，会让 Frequency 和 Monetary 双倍失真。

### 6.2 订单表

保留非空 `transactionId` → 按 `transactionId / date / visitStartTime` 排序 → 每单保留首条 → 收入 ÷1,000,000 → `orders.csv`（11,552 行）。

结果：11,552 笔订单、10,022 个购买用户、$1,627,429.54、人均 1.153 笔。

### 6.3 RFM 原始指标

- `Recency` = 快照日 − 最近订单日
- `Frequency` = 去重订单数
- `Monetary` = 累计订单收入

快照日取 `orders.order_date.max()`，**实际结果恰好是 2017-08-01**（= 观察期末日），与文档口径一致。不过依赖数据最大值是个脆弱写法，应显式指定。

### 6.4 五分位评分与分层

用 `pd.qcut` 五分位把量纲不同的 R/F/M 统一到 1–5 分（R 反向），`RFM_score` 范围 3–15。因并列值过多，先用 `rank(method="first")` 打散。

分层规则（与代码一致）：

| 客群 | 规则 |
|---|---|
| 高价值用户 | R≥4 且 F≥4 且 M≥4 |
| 忠诚用户 | F≥4 且 R≥3 |
| 新近购买用户 | R≥4 且 F≤2 |
| 风险用户 | R≤2 且 F≥3 |
| 潜力用户 | R≥3 且 F≤2 |
| 一般用户 | 其余 |

### 6.5 分层结果

| 客群 | 人数 | 人数占比 | 收入占比 | 人均 | 均 Recency |
|---|---:|---:|---:|---:|---:|
| 高价值用户 | 385 | 3.84% | **25.24%** | $1,067（6.57×） | 63.9 天 |
| 新近购买用户 | 1,510 | 15.07% | 18.91% | $204 | 69.2 天 |
| 一般用户 | 2,939 | 29.33% | 25.57% | $142 | 217.4 天 |
| 风险用户 | 2,281 | 22.76% | 12.40% | $88 | **289.3 天** |
| 潜力用户 | 771 | 7.69% | 9.05% | $191 | 184.6 天 |
| 忠诚用户 | 2,136 | 21.31% | 8.82% | $67（0.41×） | 111.4 天 |

**价值两极分化**：高价值 3.84% 人数贡献 25.24% 收入；忠诚 21.31% 人数只贡献 8.82%，两者人均价值密度相差约 16 倍。风险 + 忠诚合计 44.07% 人数，仅贡献 21.23% 收入。

## 七、第四章（续）：用户生命周期

> 这是项目名称里"生命周期"三个字的实际落点，此前只有 RFM 快照，现已补齐。

### 7.1 复购间隔

购买用户 10,022 人，其中复购用户（≥2 单）**971 人，占 9.69%**。

| 间隔 | 人数 | 占比 | 累计 |
|---|---:|---:|---:|
| 0–7 天 | 273 | 30.1% | 30.1% |
| 8–14 天 | 155 | 17.1% | 47.2% |
| 15–30 天 | 198 | 21.8% | 69.0% |
| 31–60 天 | 147 | 16.2% | 85.2% |
| 61–90 天 | 71 | 7.8% | 93.1% |
| 91–180 天 | 52 | 5.7% | 98.8% |
| 181–365 天 | 11 | 1.2% | 100% |

中位间隔 **14 天**（P25=5，P75=35），**71.06% 的二购发生在首购后 30 天内**。

### 7.2 Cohort 留存

按首购月分组，观察后续每月的复购留存：

- M1 平均留存 **3.74%**，M2 **1.79%**，M3 **1.09%**——留存曲线非常陡。
- 2016-08 的 cohort 可观察 12 个月；2017-07 的 cohort 只能观察到 M1。
- 未观察到的格子**不生成行、不记 0**，避免把"还没到"误读为"流失"。
- 2017-08 的 cohort 只覆盖 08-01 一天（34 人），样本不足已剔除。

### 7.3 累计消费曲线

人均累计消费：首购当月 **$131.18** → 第 3 月 **$154.26** → 可观察末期 **$162.39**。

**首购当月即占累计的 80.8%，前 3 个月占 95%。** 价值几乎在首单当月兑现。

### 7.4 生命周期带来的两个判断

1. **复购窗口在首购后两周内**，而不是 30 天或 90 天后。复购激活应排在首单后第 7–14 天。
2. **90.31% 的购买用户只买过一次**——这直接解释了 RFM 的 F 维度为什么区分度弱：在极度右偏的分布上做五等分，低频段必然失去区分意义。

## 八、用户主表与复合洞察

`user_master.csv`：一行一个 `fullVisitorId`（714,167 行），合并渠道、设备、新老、是否购买、RFM 客群。

其中三个聚合口径已核实：`is_new` 取"任一会话 `newVisits=1`"；`channel` 取"会话数最多的渠道，并列按名称升序"；`device` 取首个会话。

**① 高价值用户高度集中**

385 名高价值用户中，能匹配到会话属性的 356 人里：约 **55% 来自 Referral**、**97% 使用 desktop**、**90% 是首次进入的新用户**。

→ 高价值不是"老客慢慢买出来的"，而是"对的人在优质渠道一次性买得贵"。

**② 渠道决定买不买，新老决定买多少，设备是放大器**

Referral 新用户购买率 6.91%，甚至高于 Direct 回访用户 4.61%；desktop 回访购买率 8.01% 是 mobile（2.45%）的 3.3 倍。

**③ 联合结论**

`价值 ≈ 渠道意愿 × 新老强度 × 设备放大`——这是业务解释，不是统计模型，更不是因果公式。

## 九、第五章：业务洞察与七项策略

按 ROI 排序的动作清单：

1. **深挖 Organic Search 新客 desktop 冷流量池**：基数最大、落差最大，再营销 + 首单礼 + 信任模块，约 **+1,900 单**空间。
2. **重仓 Referral**：Referral × 回访 × desktop 转化 20.42%，ROI 最确定；做老客推荐双返、会员专属。
3. **商品详情页优化**：浏览→加购流失 64.53%，改信息完整性、价格/促销表达、信任元素、加购按钮可见性。
4. **购物车与结账流程优化**：加购→结账流失 61.20%，查费用展示、登录要求、结算步骤。
5. **移动端降摩擦**：mobile 2.51% vs desktop 8.77%，做免密快捷结账、一键购买。
6. **新客信任基建 + 复购激活**：新客每一步都落后，且复购窗口只有 14 天，激活动作要前移到首单后第 7–14 天。
7. **收紧伪优质渠道考核**：Affiliates 加购虚火、Social 低意图，按最终转化而非加购率考核。

## 十二、项目体现的能力

1. **数据口径意识**：先确认用户/会话/事件/订单/RFM 各自的统计单位，再谈指标。
2. **数据质量审计**：路径、字段类型、缺失、重复、候选键、跨日期冲突、编码覆盖、订单重复。
3. **多表多粒度处理**：四张表并存，不同粒度不能粗暴 JOIN，必须先定粒度再聚合。
4. **行为事件体系理解**：用 `actionType` + `hitNumber` 还原路径，理解 User / Session / Event / Channel / Device 的关系。
5. **可复现交付**：分析结果沉淀为 29 张结构化表 + 6 张图 + 4 套看板 + 5 个可重跑脚本。
6. **边界意识**：不把观察性相关写成因果，不把规则分层说成机器学习，不虚构生产级组件。

## 十三、已知弱点与不能夸大的地方

### 13.1 已知弱点（被问到应如实承认）

1. **F 维度近乎无效**：90.31% 的购买用户只买过 1 单，五分位在低频段靠 `rank` 打散，接近随机。正确做法是按业务规则分箱（1 / 2 / 3+ 次）。
2. **没有统计显著性检验**：所有分组差异都是点估计，无置信区间，只靠 1,000 浏览量阈值做替代性防护。
3. **+1,900 单含自选择偏差**，是乐观上限而非预测。
4. **漏斗起点 124,188 是选择口径**，7.31% 不能与 1.28% 比较。
5. **Referral 收入 94.47% 来自 `(direct)/(none)`**，归因存疑。
6. **观察期只有 12 个月**，无法区分"沉默"与"永久流失"。
7. **公开数据、无真实业务方**，所以"结果"只能是机会测算 + 动作清单 + 看板，不能是"提升了 X%"。

### 13.2 不能说的话

- 不说"证明了因果关系"，只说"观察到 X 与 Y 相关，提出待验证假设"。
- 不说"Referral 导致高转化"，只说"购买转化口径下效率最高，但归因存疑"。
- 不说"Social 没价值"，只说"购买转化口径下效率极低，可能更适合曝光或再营销"。
- 不把 1.2784%（Session 购买率）说成用户购买率，不把 7.305% 说成全站转化率。
- 不把 24,532（购买事件）说成 11,552（订单）。
- 不把 RFM 说成机器学习模型。
- 不说做过流失预测模型（主动放弃，理由见下）。
- 不说有实时数仓 / Kafka / Flink / Airflow / dbt / ClickHouse。
- 不虚构数据中不存在的漏斗阶段（如收藏）。

## 十四、高频追问的标准答法

**Q：为什么不用 `fullVisitorId + visitId` 做会话键？**
先构造候选键并做唯一性审计，DuckDB 六维聚合发现 898 个跨日期重复，抽样确认是不同日期的两次真实访问，于是把 `date` 纳入键；修正后 903,653 行对应 903,653 个唯一键。

**Q：为什么漏斗按 Session 而不是按用户？**
`hitNumber` 是会话内顺序，跨会话合并会把不同访问的浏览和购买错拼成一条路径；用户级分析放在 RFM 和新老对比里。

**Q：宽口径和严格漏斗的区别？**
宽口径只看行为是否出现过，会高估后段人数；严格漏斗要求 `2→3→5→6` 按顺序依次命中。

**Q：为什么购买事件不等于订单？**
同一 `transactionId` 在事件表中可出现多行，24,532 条购买事件去重后仅 11,552 笔订单；直接用会让 F/M 双倍失真。

**Q：两个收入为什么不一致？**
不同表、不同粒度；经营用 Session 表，客单价与 RFM 用订单表，差额 5.7%，不强行统一。

**Q：RFM 分层是否主观？**
是规则型相对标签，不是客观真值。而且 90.31% 的用户只买 1 单，F 维度接近无效——这是明说的局限。

**Q：为什么不做流失预测？**
评估后主动跳过。表面理由是末期没有完整观察窗，但严格说可以用滑动窗口解决。真正原因是三条：churn 标签本身主观（多久不买算流失没有业务定义）、正负样本极度不平衡、以及**这个需求已由 RFM 的风险客群覆盖**（2,281 人、平均 289 天未购、仍占 12.4% 收入）。规则分层更稳、更可解释，也能直接落到召回动作上。

**Q：怎么验证这些结论？**
不做因果宣称。验证路径是对商品详情页做 A/B：按 `fullVisitorId` 分流、按渠道×新老×设备分层，主指标取加购率（基线 35.47%）而非购买率。按 α=0.05、power=80% 计算，检测 5% 的相对提升每组约需 15,500 个会话，这个站点约跑 91 天——**所以实验必须押在有实质改动的地方，小改文案测不出来**。

## 十五、一句话总结

先用数据审计把口径和唯一键钉死，再建立全站与渠道基线，按会话还原严格转化漏斗定位真实瓶颈，通过订单去重和 RFM 分层识别用户价值，最后用 cohort 留存和复购间隔补齐"用户生命周期"这一环，并将全部结果沉淀为可复现的结构化表、图表和看板。

**最核心的能力是：不轻信原始字段，不混淆数据粒度，不把观察性相关写成因果结论——先定义口径、验证数据、计算指标、解释边界，再提出可验证的业务建议。**
